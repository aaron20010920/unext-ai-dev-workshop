# 為什麼要先寫規格，才叫 AI 動手

> 這份是今天上半場的內容。不用先讀完 — 上課會走一遍。

---

## 一、AI 寫 code 這件事，走過三個階段

| | 你做什麼 | AI 做什麼 | 你的角色 |
|---|---|---|---|
| **第一階段**（2021–2022）自動補全 | 打字 | 猜你下一行要寫什麼 | 打字的人，AI 幫你打快一點 |
| **第二階段**（2023–2024）對話生成 | 問「這段怎麼寫」 | 給你一段 code，你貼回去 | 還是你在組裝 |
| **第三階段**（2025–）**交辦執行** | 說「我要什麼」 | 自己讀你的專案、改好幾個檔、開 PR 回來 | **需求方 + 驗收方** |

Codex、Claude Code、Cursor 都在第三階段。差別不是「更聰明」，是**它會自己動手，不用你貼來貼去**。

### 這個轉變把瓶頸移到別的地方

第一、二階段的瓶頸是「你會不會寫」。

第三階段的瓶頸是 —— **你到底要什麼**。

它實作能力比你強，速度比你快一百倍。它唯一不知道的是你腦子裡那個東西。
而它**不會承認自己不知道**，它會猜，猜得非常自信、非常完整、看起來非常對。

> 今天要練的兩件事就是這兩個洞：
> **① 把願望說清楚（PRD）　② 看得出它做錯（review）**
>
> 不是學寫程式。

## 二、SDD 從哪來 — 這其實是軟體業的老問題

「需求講不清 → 做出來不是要的 → 重做」這件事，比 AI 早了五十年。

| 年代 | 解法 | 為什麼還是會出事 |
|---|---|---|
| 1970s **瀑布式** | 先寫一份超厚的規格書，簽核後才開工 | 寫的時候不知道自己要什麼，做到一半才發現 |
| 2000s **敏捷** | 不寫厚規格，兩週一個小版本，邊做邊修 | 靠「人跟人常識相通」補洞 — 工程師會自己想「這裡應該是這意思」 |
| 2025 **SDD** | 規格是唯一真相，code 是規格的產物 | ← 我們現在在這 |

### 為什麼敏捷那套用在 AI 上會壞掉

敏捷能省規格，是因為**人有常識**。

你跟工程師說「做一個登入頁」，他不用問就知道要有密碼欄、要遮住、密碼錯要提示、
不能把密碼印在 log 裡。這些沒人寫在規格上，他自己補的。

**AI 沒有這種常識，它有的是「統計上最常見的做法」** —— 那不一樣。
它會補一堆你沒要的東西（登入、資料庫、註冊流程），也會漏掉你以為理所當然的事。

所以規格重新變重要。不是因為流程要求，是因為**接單的那位不會自己補洞**。

### SDD 一句話

> **規格是你唯一真的要親手寫（或親手 review）的東西。code 是它的產物。**

code 壞了可以重生成，規格錯了，重生成幾次都是錯的。

## 三、所以 PRD 怎麼寫 — 你不用學會寫，你要學會叫人來問你

**壞消息**：你不知道要寫什麼。第一次寫 PRD 的人都不知道。

**好消息**：你不用知道。**LLM 知道要問什麼。**

所以今天的做法是三步：

```
① 許願（一句白話，不用修飾）
      ↓
② 召喚一個會問好問題的訪談員 → 它問你 6 題 → 吐出 PRD
      ↓
③ 你 review 那份 PRD ← 今天真正的技術活在這裡
```

**Prompt 全文在 [`02-prompts.md`](02-prompts.md) 的 Prompt 1。**

### 為什麼是「它問你」而不是「你寫」

因為問對問題本身就是專業。你不會問「誰驗收」「什麼算成功」「你的硬限制是什麼」，
但那三題決定了東西做不做得出來。

讓專業的來問，你只要**答得誠實**。

### 為什麼 review 才是重點

它產出 PRD 的速度是你的一百倍，準確度大概七成。

那三成錯的地方，長得跟對的一模一樣 —— 一樣有條列、一樣有標題、一樣自信。

**看得出那三成，就是你的價值。** 這也是接下來幾年你的工作長相：
不是跟 AI 比誰產得快，是看得出它哪裡不對。

Review 用什麼看 → [`../SPEC-TEMPLATE.md`](../SPEC-TEMPLATE.md) 那張六格檢查表。

### 最容易漏的那一格

**它不會主動告訴你「這個今天做不完」。**

你說要五個功能，它會五個都寫進 PRD、都寫得很可行。因為它不知道你只有 3.5 小時、
不會寫程式、只有一個輸入框。

所以 review 一定要問一句：**「今天做得完的是哪些，做不完的是哪些？」**
它會誠實回答 —— 但你要先問。

> 做不完的部分**不要刪掉**，列成一張清單。
> demo 的時候你可以說「這版先做到 X，接下來會長 Y」——
> 那比「我做不完」專業一百倍，而且是真的。

## 四、今天你其實會用到四樣東西（順手認識一下）

不用背，但知道它們的名字，之後你會一直碰到。

| 東西 | 今天在哪 | 它在幫你什麼 |
|---|---|---|
| **給 AI 的說明書** | 你 repo 根目錄的 `AGENTS.md`（要自己建） | 讓 Codex 每次都記得你是誰、紅線在哪，不用每次重講 |
| **存起來的招式** | 你自己存的那幾支 prompt | 同一件事教一次，下次貼一遍就好 |
| **派出去的分身** | Codex 本身 | 你派它去改 code，它自己開 PR 回來，不佔你的手 |
| **自動守門** | `.github/workflows/ci.yml` | 每次 push **自動**檢查 build 過不過 |

最後那個值得多講一句：

**它不是「拜託 AI 記得檢查」，它是物理攔截。** 你不會每次都記得檢查，但它每次都會跑。
這是今天唯一一個「不靠人自律」的機制 —— 這種東西越多，你的系統越可靠。

### 建一份 `AGENTS.md`（今天開工前做，30 秒）

在你 repo 的根目錄建一個 `AGENTS.md`，貼這段（改成你自己的）：

```
我是 UNEXT 見習生，在做一個個人專案，不會寫程式。

跟我合作的規則：
- 先告訴我你要改哪個檔，等我說開始再動手
- 一次只改一到兩個檔，不要一次動五個
- 改完告訴我「改了什麼、我去哪裡看效果」

紅線：
- 不要加登入、資料庫、付款、檔案上傳（今天做不完）
- 不要把 API key 寫進任何程式碼
- 不要裝新套件（不要動 package.json）
```

Codex 讀得到它。這一份寫好，後面每次對話都省下重複交代。
